계산 시간을 재고 계산량을 어림하기

본문 · 1.3절

입자 800개의 중력을 계산하는 코드가 한 걸음에 1.2초 걸린다. 이 코드로 입자 10만 개를 1,000걸음 적분하려면 얼마나 걸릴까? 돌려 놓고 기다리기 전에 미리 알 수는 없을까? 더 빠른 컴퓨터를 사는 것과 계산 방법을 바꾸는 것 가운데 무엇이 나을까?

먼저 알아야 할 것Unix 명령과 스크립트(1.1절)와 직접 합산법(3.1절)을 쓴다.

처음 질문의 답은 작은 실행으로 시간을 재고, 크기를 늘릴 때 시간이 몇 배가 되는지로 계산량의 차수를 확인하는 것이다. 차수만 알면 큰 계산의 시간을 미리 어림할 수 있다.

1.3.1시간 재기

Python에서는 time.perf_counter()로 구간의 시간을 재고, Unix 명령창에서는 time python run.py로 전체 시간을 잰다. 한 번만 재면 다른 프로그램의 영향으로 흔들리므로, 여러 번 재서 가장 짧은 값이나 중앙값을 쓴다. 또 함수별로 시간을 나눠 보려면 python -m cProfile run.py 같은 프로파일러를 쓴다.

1.3.2계산량의 차수

N체 직접 합산은 모든 쌍 \(N(N-1)/2\)개를 계산하므로 시간이 \(N^2\)에 비례할 것이다. 실제로 재 보자.

import random, time

def accelerations(pos, eps2=1e-4):
    """직접 합산: 모든 쌍의 중력 가속도 (G = m = 1)"""
    n = len(pos)
    acc = [[0.0, 0.0, 0.0] for _ in range(n)]
    for i in range(n):
        xi, yi, zi = pos[i]
        for j in range(i + 1, n):
            dx, dy, dz = pos[j][0] - xi, pos[j][1] - yi, pos[j][2] - zi
            inv = (dx * dx + dy * dy + dz * dz + eps2) ** -1.5
            acc[i][0] += dx * inv; acc[i][1] += dy * inv; acc[i][2] += dz * inv
            acc[j][0] -= dx * inv; acc[j][1] -= dy * inv; acc[j][2] -= dz * inv
    return acc

random.seed(0)
prev = None
for n in (200, 400, 800):
    pos = [[random.random() for _ in range(3)] for _ in range(n)]
    t0 = time.perf_counter()
    accelerations(pos)
    dt = time.perf_counter() - t0
    ratio = f"  (앞의 {dt / prev:.1f}배)" if prev else ""
    print(f"N = {n:4d}: {dt:.3f} s{ratio}")
    prev = dt
N =  200: 0.054 s
N =  400: 0.261 s  (앞의 4.8배)
N =  800: 1.203 s  (앞의 4.6배)

시간은 컴퓨터마다 다르지만 중요한 것은 비율이다. \(N\)을 두 배로 할 때 시간이 약 4배(\(2^2\))가 되므로 \(O(N^2)\)임이 확인된다(그림 1의 기울기). 대표적인 차수는 표 1과 같다.

표 1. 계산량의 차수
차수\(N\)을 2배로 하면예
\(O(N)\)2배합계, 평균, 히스토그램
\(O(N\log N)\)2배 조금 넘게정렬, 고속 푸리에 변환, 트리 코드
\(O(N^2)\)4배N체 직접 합산, 단순한 쌍 찾기
\(O(N^3)\)8배가우스 소거(\(N\times N\) 행렬)

1.3.3큰 계산 미리 어림하기

위 결과에서 \(N = 800\)이 1.2초이면, \(N = 10^5\)은 \((10^5/800)^2 = 15{,}600\)배인 약 5시간이 걸리고, 그것도 한 걸음뿐이다. 따라서 1,000걸음을 적분하면 약 200일이 든다. 이렇게 미리 어림하면 무엇을 할지 정할 수 있다. 배열 연산 라이브러리나 컴파일 언어로 코드를 다듬으면 수십에서 수백 배 빨라지지만, 트리 코드처럼 \(O(N\log N)\) 알고리즘으로 바꾸면 \(N = 10^5\)에서 수천 배 빨라진다. 즉 처음 질문의 마지막 답은, 큰 \(N\)에서는 알고리즘의 차수가 상수배 개선을 압도한다는 것이다.

예제 1.3.1

\(1000\times1000\) 행렬의 가우스 소거가 0.5초 걸렸다. \(4000\times4000\)이면 얼마나 걸리는가?

풀이. \(O(N^3)\)이므로 \(4^3 = 64\)배, 약 32초이다. 메모리도 \(N^2\)에 비례해 16배가 되어, 배정밀도로 8 MB에서 128 MB가 된다.

마무리

시간은 time.perf_counter()와 프로파일러로 여러 번 재서 흔들림을 줄인다. 크기를 두 배로 할 때 시간이 2, 4, 8배가 되면 차수는 각각 \(N\), \(N^2\), \(N^3\)이다. 작은 실행으로 큰 계산을 어림하고, 필요하면 코드를 다듬기보다 알고리즘의 차수를 바꾼다.

1.3.4연습문제

기본

  1. 정렬이 \(N = 10^6\)에서 1초 걸렸다면 \(N = 10^7\)은 대략 얼마인가?
    답

    \(O(N\log N)\)이므로 \(10\times\log10^7/\log10^6 = 10\times7/6\), 약 12초이다.

응용

  1. 두 목록(각 \(10^6\)개)에서 가까운 쌍을 찾을 때 모든 쌍을 비교하면 몇 번 비교하는가? 하늘을 칸으로 나눠 같은 칸과 이웃 칸만 비교하면 어떤가?
    답

    모든 쌍이면 \(10^{12}\)번이다. 칸으로 나누면 천체마다 근처 몇 개만 비교해 대략 \(10^6\)~\(10^7\)번으로 줄어든다. 교차 맞춤 프로그램이 쓰는 방법이다(천우7 6.4절).

  2. 위 코드에서 acc[j]를 빼는 줄을 지우고 j 반복을 range(n)(단 \(j \ne i\))으로 바꾸면 시간은 몇 배가 되고, 답은 같은가?
    답

    쌍마다 두 번 계산하므로 약 2배 느려진다. 힘의 대칭(작용과 반작용)을 쓰지 않을 뿐이라 답은 반올림 차이 정도로 같다.
