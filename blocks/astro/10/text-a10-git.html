버전 관리와 재현 가능한 계산

본문 · 1.2절

논문 심사위원이 그림 3을 조금 다른 매개변수로 다시 그려 달라고 한다. 석 달 전에 그린 그림인데, 어떤 코드의 어떤 판으로, 어떤 매개변수와 난수로 그렸는지 기억나지 않는다. 같은 그림조차 다시 만들 수 없다면 그 결과를 믿을 수 있을까? 어떻게 하면 석 달 뒤의 나도 결과를 재현할 수 있을까?

먼저 알아야 할 것Unix 명령(1.1절)을 쓴다.

석 달 뒤의 나는 남이나 다름없다. 재현할 수 없는 결과는 과학적 결과로 인정받기 어렵다. 처음 질문의 답은 두 가지 습관, 곧 버전 관리와 계산 조건의 기록이다.

1.2.1git의 기본

git은 코드의 변경을 커밋 단위로 기록하는 도구이다(표 1). 커밋마다 고유한 해시가 붙으므로, 나중에 그 해시로 정확히 그때의 코드를 되살릴 수 있다. 한편 큰 자료 파일이나 결과물은 .gitignore에 적어 기록하지 않는다.

표 1. 자주 쓰는 git 명령
명령하는 일
git init현재 폴더를 저장소로 만든다
git add, git commit -m "설명"변경을 커밋으로 기록한다
git log, git diff기록과 차이를 본다
git checkout 해시 -- 파일예전 판의 파일을 되살린다
git branch, git merge갈래에서 실험하고 합친다

GitHub 같은 원격 저장소에 올리면 백업이 되고 공동 연구자와 함께 쓸 수 있다. 커밋 설명은 무엇을 왜 바꿨는지를 한 줄로 쓴다. 예를 들어 "연화 길이를 0.01로 줄임, 근접 조우 에너지 오차 확인용"처럼 쓴다.

1.2.2재현 가능한 계산의 기록

코드만 기록해서는 부족하다. 먼저 결과를 만든 커밋 해시를 결과 파일 머리말이나 로그에 함께 저장한다(그림 1). 다음으로 Python과 라이브러리 판을 pip freeze > requirements.txt나 conda의 environment.yml로 기록한다. 판이 바뀌면 결과가 미세하게 달라질 수 있기 때문이다.

또 매개변수는 코드에 박지 말고 설정 파일로 두고 그 파일도 커밋하며, 자료는 출처와 내려받은 날짜를 적는다. Monte Carlo 계산은 rng = numpy.random.default_rng(42)처럼 난수 씨앗을 정해 기록한다. 끝으로 파일을 손으로 고치는 단계를 없애, 원자료에서 최종 그림까지 스크립트 하나로 다시 만들 수 있게 한다.

예제 1.2.1

MCMC 결과가 어제와 오늘 조금 다르다(\(a = 1.810\)과 \(1.840\)). 무엇을 의심해야 하는가?

풀이. 난수 씨앗이 다르면 사슬이 달라, 평균이 통계적 요동만큼, 이 경우 표준편차 0.07의 일부만큼 다를 수 있다(5.2절). 그러므로 먼저 씨앗을 고정해 같은 결과가 나오는지 확인하고, 씨앗에 따른 차이가 불확도보다 작은지 본다. 그래도 다르면 코드나 입력이 바뀐 것이므로 git diff로 확인한다.

주의Jupyter 노트북은 칸을 순서 없이 실행할 수 있어 재현성을 해치기 쉽다. 마지막에는 커널을 재시작한 뒤 모든 칸을 처음부터 실행해 같은 결과가 나오는지 확인한다.
마무리

git으로 코드의 변경을 커밋 단위로 기록하고, 갈래에서 실험하며, 언제든 예전 판으로 되돌린다. 결과와 함께 커밋 해시, 환경의 판, 설정 파일, 난수 씨앗을 기록하면 결과를 다시 만들 수 있다. 원자료에서 그림까지 스크립트 하나로 다시 만들 수 있게 하는 것이 재현 가능한 계산의 목표이다.

1.2.3연습문제

기본

  1. 방금 고친 내용을 커밋하기 전에 무엇이 바뀌었는지 보는 명령은 무엇인가?
    답

    git diff이다.

응용

  1. 공동 연구자가 같은 코드로 다른 결과를 얻었다. 확인할 것 세 가지를 들어라.
    답

    같은 커밋인지, 라이브러리 판이 같은지, 입력과 설정과 난수 씨앗이 같은지 확인한다.

  2. 논문 그림 파일의 이름이나 머리말에 커밋 해시를 넣으면 어떤 점이 좋은가?
    답

    그림이 어떤 코드 판에서 나왔는지 나중에 바로 알 수 있어, 그 판을 되살려 같은 그림을 다시 만들 수 있다.
