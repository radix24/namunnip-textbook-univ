순환 부호와 CRC

본문

이더넷 프레임 끝에는 32비트짜리 덧붙임이 있어, 수신기는 이것만 보고 프레임이 망가졌는지 알아낸다. 고칠 수는 없어도 틀렸다는 사실만은 확실히 알 수 있는 방법은 무엇일까? 그 계산은 왜 하드웨어로 그토록 빠르게 할 수 있을까?

먼저 알아야 할 것선형 블록 부호(5.1절), XOR을 쓴다.

5.3.1나머지를 붙인다

비트열을 다항식의 계수로 보면, 1101은 \(x^3 + x^2 + 1\)이 된다. 이때 덧셈과 뺄셈은 모두 XOR이다. CRC는 메시지 다항식에 \(x^r\)을 곱하고(r개의 0을 붙이고) 생성 다항식 G로 나눈 나머지를 붙여 보낸다. 그러면 받은 비트열 전체가 G로 나누어떨어진다(그림 1). 그래서 수신측에서 다시 나눈 나머지가 0이 아니면 오류이다. 처음 질문의 첫째 답이 이것이다.

나눗셈은 자리 이동과 XOR만으로 되므로, 시프트 레지스터 몇 개와 XOR 게이트로 비트가 들어오는 속도 그대로 계산할 수 있다. 처음 질문의 둘째 답이 이것이다. 아래 코드는 이 나눗셈을 그대로 따라 한다.

def crc(bits, gen):
    r = len(gen) - 1
    a = list(map(int, bits + "0" * r))
    g = list(map(int, gen))
    for i in range(len(bits)):
        if a[i]:
            for j in range(len(g)):
                a[i + j] ^= g[j]
    return "".join(map(str, a[-r:]))
msg, gen = "1101011011", "10011"         # 생성 다항식 x⁴ + x + 1
rem = crc(msg, gen)
print("CRC:", rem, " 보내는 비트열:", msg + rem)
print("수신 검사(오류 없음) 나머지:", crc(msg + rem, gen)[-4:] if False else crc((msg + rem)[:-4], gen) == rem)
bad = "1101111011" + rem                 # 한 비트 뒤집힘
print("오류 있는 수신의 재계산 CRC:", crc(bad[:-4], gen), "→ 받은 CRC와 다름:", crc(bad[:-4], gen) != rem)

실행 결과(Python 3.12에서 실제 실행)는 다음과 같다.

CRC: 1110  보내는 비트열: 11010110111110
수신 검사(오류 없음) 나머지: True
오류 있는 수신의 재계산 CRC: 0100 → 받은 CRC와 다름: True
예제 5.3.1

위 메시지 1101011011, 생성 다항식 10011의 CRC는? 한 비트가 뒤집히면?

풀이. 실행 결과에서 CRC는 1110이고, 보내는 비트열은 11010110111110이다. 한 비트가 뒤집히면 다시 계산한 CRC가 0100으로 받은 것과 달라 오류를 검출한다. 이더넷은 이런 32비트 CRC로 프레임 오류를 거른다.

생성 다항식을 잘 고르면 CRC는 특히 연달아 몰려 생기는 버스트 오류에 강하다. 즉 짧은 버스트는 빠짐없이 잡고, 그보다 긴 오류도 대부분 잡는다. 그래서 같은 수의 검사 비트를 쓰는 단순한 패리티나 체크섬보다 훨씬 믿을 만하다.

실제 규격은 생성 다항식을 이름으로 정해 둔다. 예를 들어 CRC-16-CCITT는 블루투스와 여러 직렬 통신에, CRC-32는 이더넷과 ZIP 파일에 쓰인다. 그리고 송신기와 수신기가 같은 다항식을 써야만 검사가 맞으므로, 다항식은 규격의 일부로 고정된다.

흔한 오해CRC가 오류를 고친다고 여기기 쉽다. CRC는 검출만 하며, 고치는 일은 재전송이나 정정 부호가 맡는다. 또 CRC가 모든 오류를 잡는다고 생각하기 쉬운데, 오류 패턴이 마침 생성 다항식의 배수이면 놓친다. 다만 그런 경우는 매우 드물다.
마무리

CRC는 \(x^rM(x)\)를 G(x)로 나눈 나머지를 붙여 보낸다. 수신측에서 나머지가 0이 아니면 오류로 판정한다. 메시지 1101011011, 생성 다항식 10011이면 CRC는 1110이다.
