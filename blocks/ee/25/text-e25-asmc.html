어셈블리와 C로 마이크로컨트롤러 프로그래밍

본문

마이크로컨트롤러 펌웨어는 대부분 C로 쓰지만, 시동 코드나 디버거 화면에서는 어셈블리를 만나게 된다. C의 for 문 하나는 실제로 어떤 명령어 몇 개로 바뀔까? 그리고 하드웨어 레지스터의 특정 비트만 켜고 끄는 일은 C로 어떻게 쓸까?

먼저 알아야 할 것프로그래밍 모델(1.1절), C 기초(공통 프로그래밍)를 쓴다.

1.2.1같은 일을 두 언어로

배열 a의 n개 원소 합을 구하는 C 함수와, 이를 손으로 옮긴 Thumb-2 어셈블리이다. 여기서 R0은 주소, R1은 개수이며 결과는 R0에 담긴다.

int sum(const int *a, int n) {
    int s = 0;
    for (int i = 0; i < n; i++) s += a[i];
    return s;
}
sum:    MOVS  r2, #0          @ s = 0
loop:   CBZ   r1, done        @ n == 0이면 끝
        LDR   r3, [r0], #4    @ r3 = *a, a += 4 (사후 증가)
        ADDS  r2, r2, r3      @ s += r3
        SUBS  r1, r1, #1      @ n--
        B     loop
done:   MOV   r0, r2          @ 반환값
        BX    lr

원소 하나에 명령어 다섯 개(LDR, ADDS, SUBS, B, CBZ)가 돈다(그림 1). 처음 질문의 첫째 답이 이것이다. 그런데 컴파일러 최적화(-O2)는 루프를 펼치거나 비교를 줄여 더 빠른 코드를 만들기도 한다. 그래서 대부분은 C로 쓰고, 시동 코드나 시간이 엄격한 부분만 어셈블리로 쓴다.

예제 1.2.1

32비트 레지스터 reg에서 비트 3을 1로, 비트 7을 0으로, 비트 4를 검사하는 C 식은?

풀이. 차례로 reg |= (1u << 3);, reg &= ~(1u << 7);, if (reg & (1u << 4))이다. 처음 질문의 둘째 답이 이 세 식이다.

그런데 읽고-바꾸고-쓰기 중간에 인터럽트가 같은 레지스터를 바꾸면 값이 덮어써질 수 있다. 따라서 비트 설정 전용 레지스터(SET/RESET)나 인터럽트 금지 구간을 쓴다.

즉 어셈블리를 읽을 줄 알면 컴파일러가 만든 코드가 의도대로인지, 루프 안에 불필요한 메모리 접근이 남았는지를 디버거에서 바로 확인할 수 있다. 그래서 C로 쓰더라도 시간이 중요한 함수는 디스어셈블 결과를 한 번 보는 습관이 도움이 된다.

한편 비트 연산에서 1u처럼 부호 없는 상수를 쓰는 이유도 있다. 부호 있는 1을 31비트만큼 밀면 부호 비트에 닿아 C 표준에서 정의되지 않은 동작이 되므로, 레지스터 비트를 다룰 때는 언제나 부호 없는 형식으로 계산한다.

흔한 오해어셈블리가 언제나 C보다 빠르다고 여기기 쉽다. 현대 컴파일러가 대부분 더 낫다. 또 int가 언제나 32비트라고 생각하기 쉬운데, 플랫폼마다 다르므로 고정 폭 형식(uint32_t)을 쓴다.
마무리

C와 어셈블리는 LDR 사후 증가, CBZ, BX lr처럼 대응한다. 비트 설정은 |=, 해제는 &= ~, 검사는 &로 한다. 읽고-바꾸고-쓰기의 경쟁 조건에 주의한다.

1.2.2연습문제

기본

  1. reg의 비트 0~3을 모두 0으로 만드는 식은?
    답

    reg &= ~0xFu;로 쓴다.

응용

  1. LDR r3, [r0], #4 뒤 r0는 얼마나 바뀌는가?
    답

    4만큼 증가한다(다음 int).

심화

  1. 위 어셈블리에서 n = 0으로 호출하면 결과는?
    답

    CBZ로 바로 done으로 가서 0을 반환한다.
