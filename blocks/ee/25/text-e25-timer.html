타이머 인터럽트로 주기 작업 구현

본문

센서 값을 정확히 1 ms마다 읽고 LED를 0.5초마다 깜빡이게 하고 싶다. 주 루프에 delay()를 넣어 기다리면 될 것 같지만, 루프 안의 다른 일이 늘어날수록 간격이 들쭉날쭉해진다. 하드웨어 타이머로 원하는 주기를 만들려면 레지스터에 어떤 값을 넣어야 할까? 그리고 타이머 방식은 왜 더 정확할까?

먼저 알아야 할 것인터럽트 처리(2.1절)를 쓴다.

2.2.1주기 계산

타이머의 주기는 \(T = (PSC + 1)(ARR + 1)/f_{clk}\)이다. 그런데 16비트 타이머는 ARR + 1 ≤ 65536이므로, 긴 주기에는 분주가 필요하다. 처음 질문의 첫째 답이 이 식이며, 아래 코드는 16 MHz 입력에서 알맞은 조합을 찾는다.

# 16비트 타이머로 원하는 주기를 만드는 분주비(PSC)와 자동 재적재 값(ARR) 찾기
f_clk = 16_000_000          # 타이머 입력 클록 16 MHz
for period in (1e-3, 0.5):  # 1 ms, 0.5 s
    counts = round(f_clk * period)
    for psc in range(1, 65537):
        if counts % psc == 0 and counts // psc <= 65536:
            arr = counts // psc
            break
    print(f"주기 {period} s: 총 {counts} 클록 = 분주 {psc} × 계수 {arr} → PSC = {psc - 1}, ARR = {arr - 1}")

실행 결과는 아래와 같다(Python 3.12에서 실제 실행).

주기 0.001 s: 총 16000 클록 = 분주 1 × 계수 16000 → PSC = 0, ARR = 15999
주기 0.5 s: 총 8000000 클록 = 분주 125 × 계수 64000 → PSC = 124, ARR = 63999

즉 1 ms는 분주 없이 16000까지 세면 되고, 0.5 s는 16비트 한계를 넘으므로 125로 분주한 뒤 64000까지 센다(그림 1). 그리고 ISR의 예는 아래와 같다(레지스터 이름은 STM32 계열 예시이며 확인 필요).

volatile uint32_t ticks = 0;
void TIM2_IRQHandler(void) {
    if (TIM2->SR & TIM_SR_UIF) {
        TIM2->SR &= ~TIM_SR_UIF;     // 원인 플래그 지우기
        ticks++;                     // 1 ms마다 증가
        if (ticks % 500 == 0) GPIOA->ODR ^= (1u << 5);   // 0.5 s마다 LED 반전
    }
}
예제 2.2.1

1 kHz 표본화가 필요한데 주기가 1 % 이상 흔들리면 안 된다. 주 루프에서 delay()로 기다리는 방식과 타이머 인터럽트를 비교하여라.

풀이. delay 방식은 루프 안 다른 일의 시간이 더해져 주기가 흔들린다. 반면 타이머는 하드웨어가 세므로 ISR 진입 지연(수 μs 이하)만큼만 흔들린다. 처음 질문의 둘째 답이 이것이다. 그리고 더 정확하게는 타이머가 ADC를 직접 트리거하고 DMA로 저장한다(4.2절).

한편 타이머는 주기 인터럽트 말고도 쓰임이 많다. 즉 입력 신호의 가장자리 시각을 잡는 입력 캡처, 정해진 값에서 핀을 바꾸는 출력 비교, 그리고 4.3절의 PWM이 모두 같은 계수기를 바탕으로 한다. 그래서 타이머 하나의 계수 방식을 이해하면 나머지 기능도 같은 식으로 읽을 수 있다.

예를 들어 48 MHz 클록에서 1 μs 단위로 세고 싶으면 먼저 분주로 계수 클록을 1 MHz로 만든 뒤, 원하는 주기만큼의 계수 값을 ARR에 넣는다. 이렇게 분주와 계수를 나눠 생각하면 주기 계산이 단순해진다.

흔한 실수PSC에 분주비를 그대로 넣기 쉽다. 레지스터 값은 분주비 − 1이다. 또 ticks를 32비트로 세면 영원히 넘치지 않는다고 여기기 쉬운데, 언젠가는 넘치므로 시간 차이 계산을 부호 없는 뺄셈으로 한다.
마무리

타이머 주기는 T = (PSC + 1)(ARR + 1)/f_clk이다. 16 MHz에서 1 ms는 PSC 0, ARR 15999이다. 하드웨어 타이머는 소프트웨어 지연보다 정확하다.
