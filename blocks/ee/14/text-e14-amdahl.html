Amdahl 법칙

본문

프로그램 실행 시간의 80%를 곱셈이 차지한다. 곱셈기를 10배, 아니 100배 빠르게 만들면 프로그램도 그만큼 빨라질까? 곱셈기에 돈을 아무리 들여도 넘을 수 없는 벽이 있다면, 그 벽은 어디에 있을까?

먼저 알아야 할 것CPU 성능 식(1.1절)을 쓴다.

1.2.1식

원래 실행 시간을 1로 두고, 그 가운데 비율 \(f\)인 부분만 \(s\)배 빠르게 한다고 하자. 그러면 개선하지 않은 부분은 \(1 - f\) 그대로 남고, 개선한 부분은 \(f/s\)로 줄어 새 실행 시간은 \((1 - f) + f/s\)가 된다. 전체 가속은 그 역수이다.

\[ \text{전체 가속} = \frac{1}{(1 - f) + f/s} \;\xrightarrow{s \to \infty}\; \frac{1}{1 - f}. \]

이것이 Amdahl 법칙이다. \(s\)를 한없이 키워도 남는 \(1 - f\) 때문에 가속은 \(1/(1 - f)\)를 넘지 못한다. 처음 질문의 벽이 바로 이 상한이다.

예제 1.2.1

실행 시간의 80%가 곱셈인 프로그램. (가) 곱셈기를 10배 빠르게 하면? (나) 100배면? (다) 전체를 4배 빠르게 하려면 곱셈을 몇 배 빠르게 해야 하는가?

풀이. (가)는 \(1/(0.2 + 0.08) = 3.57\)배, (나)는 \(1/(0.2 + 0.008) = 4.81\)배이다. 상한 5배에 거의 닿아, 10배에서 100배로 늘린 노력이 35%만 더 준다(그림 1). (다)는 \(1/(0.2 + 0.8/s) = 4\)에서 \(s = 16\)이다. 반면 전체 5배는 \(s\)가 무한대여야 하므로 불가능하다.

그러므로 개선 효과는 빠르게 포화한다. 한 부분을 계속 다듬기보다, 남은 부분 가운데 가장 큰 것을 찾아 손대는 편이 낫다.

1.2.2병렬 처리

같은 생각을 다중 코어에 쓸 수 있다. 병렬화할 수 있는 비율이 \(p\)인 프로그램을 \(N\)코어에서 돌리면 가속은 \(1/((1 - p) + p/N)\)이다. 가령 \(p = 0.95\)여도 코어를 아무리 늘려 봐야 20배를 넘지 못한다.

그래서 병렬 프로그램에서는 동기화나 입출력처럼 한 코어만 일하는 직렬 부분을 줄이는 것이 핵심이다. 한편 코어가 많아질 때 문제 크기도 함께 키우는 경우는 직렬 비율이 상대적으로 줄어드는데, 이것은 Gustafson 법칙으로 다룬다.

흔한 오해가장 느린 부분을 \(s\)배 빠르게 하면 전체도 \(s\)배 빨라진다고 여기기 쉽다. 하지만 전체 가속은 개선한 부분이 차지하던 비율 \(f\)에 묶여 있어서, \(f = 0.8\)이면 아무리 해도 5배가 최대이다. 비율 \(f\)는 개선하기 전의 실행 시간에서 재야 한다는 점도 자주 틀린다.
마무리

비율 \(f\)를 \(s\)배 빠르게 하면 전체 가속은 \(1/((1 - f) + f/s)\)이고, 상한은 \(1/(1 - f)\)이다. 그래서 개선 효과는 빠르게 포화하며, \(f = 0.8\)이면 최대 5배이다. 병렬 처리의 가속 \(1/((1 - p) + p/N)\)도 직렬 부분이 한계를 정한다.

1.2.3연습문제

기본

  1. f = 0.5, s = 2이면 전체 가속은?
    답

    1/(0.5 + 0.25) = 1.33배이다.

응용

  1. p = 0.9 프로그램을 8코어로 돌리면 가속은?
    답

    1/(0.1 + 0.1125) = 4.71배이다.

심화

  1. f = 0.6 부분을 3배, 다른 0.3 부분을 2배 빠르게 하면 전체 가속은?
    답

    새 시간이 0.1 + 0.2 + 0.15 = 0.45이므로 가속은 2.22배이다.
