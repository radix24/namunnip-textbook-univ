TLB와 실효 메모리 접근 시간

본문

가상 메모리를 쓰면 데이터를 읽을 때마다 먼저 페이지 테이블을 읽어 물리 주소를 알아내야 한다. 페이지 테이블이 2단계라면 메모리 접근 한 번이 세 번으로 늘어나는 셈인데, 그러면 컴퓨터가 세 배 느려질까? 이 비용을 거의 없애는 방법은 무엇일까?

먼저 알아야 할 것가상 주소 변환(6.3절)을 쓴다.

6.5.1주소 변환도 캐시한다

가상 주소마다 페이지 테이블을 읽으면, 다단계 테이블에서는 단계 수만큼 메모리를 더 읽어 접근이 몇 배로 느려진다. 그런데 프로그램은 같은 페이지를 짧은 시간 안에 여러 번 쓰므로, 최근에 한 변환을 기억해 두면 대부분 다시 쓸 수 있다.

이 일을 하는 작은 연관 캐시가 TLB(translation lookaside buffer)이다. TLB가 적중하면 페이지 테이블을 읽지 않고 바로 물리 주소를 얻는다. 처음 질문의 둘째 답이 이것이다. TLB가 실패할 때만 페이지 테이블을 \(k\)단계 읽어 변환을 TLB에 채운다. 그래서 적중률을 \(h\)라 하면 실효 접근 시간은 다음과 같다.

\[ t_{\text{실효}} = h(t_{TLB} + t_{mem}) + (1 - h)(t_{TLB} + k\,t_{mem} + t_{mem}) \]
예제 6.5.1

TLB 조회 1 ns, 메모리 접근 100 ns, 2단계 페이지 테이블(실패 시 2번 더 읽음). TLB 적중률 98%의 실효 접근 시간은?

풀이. 적중하면 1 + 100 = 101 ns이고, 실패하면 페이지 테이블을 두 번 더 읽어 1 + 200 + 100 = 301 ns이다. 따라서 실효 시간은 0.98 × 101 + 0.02 × 301 = 105 ns이다. TLB가 없을 때의 300 ns와 비교하면 약 1/3이다(그림 1). 처음 질문의 첫째 답이 이것으로, TLB가 있으면 세 배 느려지지 않는다.

이때 TLB가 한 번에 덮는 메모리 범위를 TLB reach라 하며, 항목 수 × 페이지 크기이다. 프로그램이 쓰는 데이터가 reach보다 크면 TLB 실패가 잦아지므로, 큰 페이지를 써서 reach를 넓히기도 한다(연습문제 2).

흔한 실수TLB가 실패하면 페이지 부재가 난다고 여기는 실수가 흔하다. TLB 실패는 변환이 TLB에 없을 뿐이어서 페이지 테이블을 읽으면 해결되고, 페이지 부재는 페이지 자체가 메모리에 없어 디스크에서 읽어야 하는 훨씬 드물고 비싼 사건이다. 또 실패한 경우에도 데이터 접근 한 번은 여전히 필요하다는 점을 빠뜨리기 쉽다.
마무리

실효 접근 시간은 \(h(t_{TLB} + t_{mem}) + (1 - h)(t_{TLB} + k\,t_{mem} + t_{mem})\)이다. 예제에서 적중률 98%이면 105 ns로, TLB가 없을 때의 약 1/3이다. TLB reach는 항목 수 × 페이지 크기이다.

6.5.2연습문제

기본

  1. TLB 64항목, 4 KB 페이지의 reach는?
    답

    64 × 4 KB = 256 KB이다.

응용

  1. 같은 TLB에 2 MB 큰 페이지를 쓰면 reach는?
    답

    64 × 2 MB = 128 MB이다.

심화

  1. 적중률 99.5%면 예제의 실효 시간은?
    답

    0.995 × 101 + 0.005 × 301 = 약 102 ns이다.
