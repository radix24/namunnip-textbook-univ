소켓으로 클라이언트-서버 프로그램 작성

본문

채팅 프로그램이나 게임 서버는 결국 두 프로그램이 네트워크를 사이에 두고 바이트를 주고받는 일이다. 운영체제는 이를 위해 소켓이라는 창구를 마련해 준다. 서버와 클라이언트는 소켓을 어떤 순서로 열고 이을까? 그리고 여러 사용자가 동시에 접속하면 서버는 어떻게 바뀌어야 할까?

먼저 알아야 할 것계층과 포트(1.2절), Python 기초를 쓴다.

2.1.1순서

서버는 socket을 만들고, bind로 주소와 포트에 묶고, listen으로 연결을 기다린다. 그리고 accept가 연결마다 새 소켓을 돌려주면 그 소켓으로 recv/send를 한 뒤 close한다. 처음 질문의 첫째 답이 이 순서이다(그림 1).

한편 클라이언트는 socket을 만들고 connect로 서버 주소와 포트에 연결한 뒤, send/recv를 하고 close한다. 아래 코드는 서버를 스레드로 띄우고, 같은 프로그램에서 클라이언트로 접속한다(127.0.0.1, 운영체제가 고른 빈 포트).

import socket, threading
srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.bind(("127.0.0.1", 0)); srv.listen(1)
port = srv.getsockname()[1]
def serve():
    conn, addr = srv.accept()
    with conn:
        data = conn.recv(1024)
        conn.sendall(data.upper())
t = threading.Thread(target=serve); t.start()
cli = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
cli.connect(("127.0.0.1", port))
cli.sendall("hello, network".encode())
print("서버 응답:", cli.recv(1024).decode())
cli.close(); t.join(); srv.close()

서버 응답: HELLO, NETWORK
예제 2.1.1

위 서버가 한 번에 한 클라이언트만 처리한다. 동시에 100명이 접속하면 어떻게 고치는가?

풀이. accept를 반복하며 연결마다 스레드를 만들거나(threading), asyncio로 한 스레드에서 여러 연결을 번갈아 처리한다. 처음 질문의 둘째 답이 이것이다. 그런데 TCP는 바이트 흐름이라, recv 한 번이 보낸 메시지 하나와 일치한다는 보장이 없다. 그래서 길이 머리말이나 구분자로 메시지 경계를 정해야 한다.

즉 스레드 방식은 코드가 단순하지만 연결이 수천 개가 되면 스레드마다 드는 메모리와 전환 비용이 커진다. 그러므로 동시 접속이 아주 많은 서버는 asyncio처럼 한 스레드가 여러 연결을 돌아가며 처리하는 이벤트 방식을 쓴다.

한편 실제 서비스에서는 소켓 위에 HTTP 같은 응용 계층 프로토콜을 올리고, 그 처리는 웹 프레임워크가 맡는다. 따라서 소켓을 직접 다루는 일은 드물지만, 지연과 오류의 원인을 찾을 때는 이 아래층의 동작을 알아야 한다.

흔한 오해send 한 번이 recv 한 번과 짝을 이룬다고 여기기 쉽다. TCP는 메시지 경계를 보존하지 않는다. 또 서버 소켓으로 데이터를 주고받는다고 생각하기 쉬운데, accept가 돌려준 연결 소켓으로 주고받는다.
마무리

서버는 bind, listen, accept를, 클라이언트는 connect를 쓴다. 예제 프로그램은 HELLO, NETWORK를 돌려받는다(실제 실행). 동시 처리는 스레드나 asyncio로 하며, 메시지 경계는 직접 정한다.
