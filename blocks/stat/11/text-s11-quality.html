모델링보다 먼저

기업 자료는 분석을 위해 만들어진 것이 아니라 업무 시스템의 부산물입니다. 같은 고객이 여러 ID를 가지거나, 시스템 교체 시점에 단위가 바뀌거나, 테스트 계정이 섞여 있는 일이 흔합니다.

2.1.1점검 목록

  1. 한 행이 무엇인가: 거래 한 건? 고객 하루? 이것을 모르면 집계가 틀립니다.
  2. 열쇠: 고유해야 할 ID에 중복이 있나(duplicated)?
  3. 기간: 날짜 범위, 빠진 날짜, 시간대.
  4. 결측: 열별 결측률, 결측이 특정 기간·집단에 몰렸나.
  5. 값의 범위: 음수 금액, 미래 날짜, 999 같은 특수값.
  6. 분포의 변화: 월별 건수·평균을 그려 갑작스러운 계단(시스템 변경)을 찾음.

2.1.2큰 자료 다루기

메모리에 다 올라가지 않으면 표본을 먼저 뽑아 탐색하고, 데이터베이스(SQL)에서 집계한 결과만 가져오거나, data.table, arrow, duckdb, polars 같은 도구를 씁니다. 집계는 가능하면 자료가 있는 곳(데이터베이스)에서 합니다.

-- SQL로 월별 건수와 결측률 확인
SELECT strftime('%Y-%m', order_date) AS ym, COUNT(*) AS n,
       AVG(CASE WHEN amount IS NULL THEN 1.0 ELSE 0 END) AS na_rate
FROM orders GROUP BY ym ORDER BY ym;
예제 2.1.1

월별 주문 수 그래프에서 특정 달 이후 주문 수가 갑자기 두 배가 되었습니다. 무엇을 확인하나요?

풀이. 실제 사업 변화(행사, 신규 지역)인지, 자료 변화(주문을 상품 단위로 나눠 기록하기 시작, 중복 적재, 테스트 계정 포함)인지 업무 담당자에게 확인합니다. 자료 변화라면 정의를 맞춰 다시 집계합니다.

요약
  1. 행의 단위, 열쇠, 기간, 결측, 범위, 분포 변화를 점검.
  2. 발견한 문제와 처리를 자료 사전·기록으로 남김.
  3. 큰 자료는 표본 탐색과 데이터베이스 집계.

2.1.2연습문제

기본

  1. 고객 테이블의 행 수가 100만인데 고유 고객 ID가 98만 개입니다. 가능한 원인은?
    답

    주소 변경 등으로 이력을 행으로 쌓은 구조(한 고객 여러 행), 중복 적재, 탈퇴 후 재가입. 행의 정의를 확인합니다.
