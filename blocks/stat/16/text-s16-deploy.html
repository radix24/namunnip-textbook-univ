배치 예측과 실시간 API

본문

이탈 점수 모형과 사기 탐지 모형을 함께 배포해야 한다. 이탈 점수는 매일 밤 한꺼번에 계산해 두면 되는데, 사기 탐지도 그렇게 해도 될까? 카드 결제 요청이 들어온 순간에 판정해야 하는 모형은 무엇이 달라야 할까?

먼저 알아야 할 것회고(4.2절), 파이프라인 객체(2.4절), 정기 실행(2.5절)을 쓴다.

처음 질문의 답은 그렇게 할 수 없다는 것이다. 사기 탐지는 예측 대상인 거래가 요청 순간에야 생기므로, 미리 계산해 둘 것이 없다. 학습한 모형이 쓰이려면 예측이 업무 시스템에 전달되어야 하는데, 그 길은 둘이다(그림 1). 정해진 때에 대상 전체를 한꺼번에 예측해 표로 넘기는 배치 예측과, 요청이 올 때마다 하나씩 예측해 바로 돌려주는 실시간 API이다.

4.3.1비교

표 1. 배치 예측과 실시간 API
배치 예측실시간 API
예측 시점매일 밤 등 정기요청 즉시
입력 신선도마지막 실행 시점요청 시점

운영 부담작음(2.5절의 정기 작업)큼(서버, 확장, 장애 대응)

따라서 결정이 하루 단위로 이루어지면 배치로 충분하다. 반면 예측 대상이 새 거래처럼 요청 순간에야 정해지거나, 몇 초 전의 행동이 예측에 중요하면 실시간이 필요하다.

예제 4.3.1

고객 200만 명의 이탈 점수를 매일 계산한다. 초당 5000건을 예측할 수 있다면 배치 실행에 몇 분이 걸리는가?

풀이. \(2{,}000{,}000/5000 = 400\)초, 곧 약 6.7분이다. 그러므로 매일 밤 실행해도 아침 업무 전에 충분히 끝나, 이탈 점수에는 배치가 알맞다(그림 1).

4.3.2배포 전 점검

배포 전에는 몇 가지를 점검한다. 먼저 학습과 운영에서 같은 파이프라인 객체와 패키지 버전을 쓰는지 확인한다. 다음으로 같은 사례 몇 개를 골라, 운영 입력으로 계산한 예측이 오프라인 예측과 같은지 대조한다. 그리고 입력이 비거나 이상할 때 기본값을 쓸지 오류를 돌려줄지 정해 두고, 이전 모형으로 되돌리는 방법을 마련한다.

흔한 실수

배포 뒤 운영 예측과 오프라인 예측이 일부 고객에서 다르면, 가장 먼저 학습과 운영의 전처리나 변수 계산 방식의 차이를 의심한다. 이를 training-serving skew라 하며, 같은 고객의 입력 변수를 두 경로에서 뽑아 열마다 비교해 찾는다.

마무리

배치 예측은 정기적으로 전체를 계산해 단순하고, 실시간 API는 요청 즉시 예측하지만 운영 부담이 크다. 그러므로 결정의 주기와 필요한 입력 신선도로 고르며, 배포 전에는 같은 파이프라인과 버전, 오프라인 대조, 예외 처리, 되돌리기를 준비한다.

4.3.3연습문제

기본

  1. 상품 추천을 하루 한 번 배치로 계산하면 어떤 한계가 있는가?
    답

    오늘 방금 본 상품이 추천에 반영되지 않고, 오늘 가입한 신규 고객에게는 추천이 없다. 기본 추천은 배치로, 최근 행동은 가벼운 실시간 보정으로 나누는 절충도 가능하다.

응용

  1. 사기 탐지 API가 결제 승인 전 50 ms 안에 답해야 한다. 예측 하나에 30 ms, 변수 조회에 40 ms가 걸린다. 어떻게 하는가?
    답

    합이 70 ms라 기준을 넘는다. 자주 쓰는 고객 변수를 미리 계산해 빠른 저장소에 두어 조회 시간을 줄이고, 기준을 넘으면 규칙 기반 판정으로 대신하는 기본 동작을 정한다.

  2. 예제 4.3.1에서 고객이 2000만 명으로 늘면 배치 실행은 얼마나 걸리는가?
    답

    4000초, 약 67분이다. 여전히 밤사이에 끝나지만, 늘어날 것에 대비해 병렬 실행을 검토한다.
