Git 브랜치와 코드 리뷰

본문
이 절에서 배울 것
  • 기능 브랜치를 만들어 작업하고 병합 요청을 올린다.
  • 분석 코드 리뷰에서 무엇을 확인할지 안다.
  • 병합 충돌을 해결한다.
먼저 알아야 할 것
  • 프로젝트 일정 (1.3절), 재현 가능한 보고서 (응통3 6장).

여럿이 같은 코드를 고친다

"최종_진짜최종_v3.R" 같은 파일 이름으로는 팀 작업을 관리할 수 없습니다. Git은 모든 변경의 이력을 남기고, 브랜치로 각자의 작업을 분리했다가 검토 후 합치게 해 줍니다.

1.4.1기능 브랜치 흐름

git switch main
git pull                          # 최신 main 받기
git switch -c feature/churn-features
# ... 코드 수정 ...
git add src/features.py
git commit -m "가입 기간 변수 추가"
git push -u origin feature/churn-features
# 웹에서 병합 요청(pull request) 열기

main은 언제나 실행되는 상태로 두고, 모든 변경은 브랜치에서 하고 리뷰를 거쳐 합칩니다. 커밋은 하나의 논리적 변경 단위로 작게 나누고, 메시지에 "무엇을 왜"를 씁니다.

1.4.2분석 코드 리뷰의 점검 항목

  • 재현성: 난수 시드, 패키지 버전, 경로가 고정되어 있는가.
  • 정보 누수: 검증 자료나 미래 정보가 학습에 들어가지 않았는가(2.3절).
  • 자료 단위: 결합 후 행 수가 맞는가.
  • 비밀 정보: 비밀번호, 개인정보가 코드나 커밋에 없는가(1.2절).
  • 큰 자료 파일은 저장소에 넣지 않았는가(.gitignore).

1.4.3병합 충돌

두 브랜치가 같은 줄을 다르게 고치면 Git은 자동으로 합치지 못하고 <<<<<<<, =======, >>>>>>> 표시로 두 내용을 보여 줍니다. 어느 쪽(또는 둘을 합친 것)이 맞는지 판단해 표시를 지우고 커밋합니다. 충돌을 줄이려면 브랜치를 오래 두지 말고 자주 main을 받아 합칩니다.

예제 1.4.1

리뷰 중 df = pd.read_csv("C:/Users/kim/Desktop/data.csv")와 model.fit(X, y)(시드 없음, 랜덤 포레스트)를 발견했습니다. 어떤 의견을 남기나요?

풀이. 개인 컴퓨터 경로는 다른 사람이 실행할 수 없으므로 설정 파일이나 상대 경로로 바꾸도록, 랜덤 포레스트는 실행마다 결과가 달라지므로 random_state를 고정하도록 요청합니다.

요약
  1. main은 깨끗하게, 작업은 브랜치에서, 병합은 리뷰 후.
  2. 분석 리뷰는 재현성, 누수, 자료 단위, 비밀 정보를 봅니다.
  3. 충돌은 자주 합쳐 줄이고, 판단해서 해결합니다.

1.4.4연습문제

기본

  1. 실수로 비밀번호가 든 설정 파일을 커밋해 원격에 올렸습니다. 파일을 지우는 새 커밋만으로 충분한가요?
    답

    아닙니다. 이력에 남아 있으므로 비밀번호를 즉시 바꾸고, 필요하면 관리자와 함께 이력에서 제거합니다. 앞으로는 설정 파일을 .gitignore에 넣습니다.

응용

  1. 노트북(.ipynb) 파일은 리뷰하기 어렵습니다. 왜 그런지와 대안을 쓰세요.
    답

    출력과 메타데이터가 JSON으로 저장되어 변경 내용이 길고 읽기 어렵습니다. 핵심 로직은 .py 모듈로 옮기고 노트북은 호출과 시각화만 하게 하거나, 출력을 지우고 커밋하는 도구를 씁니다.
